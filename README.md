# bili-topic-block

DSH（DeepSeek Harness）插件：给一个 B 站视频链接，**免登录只读**地识别它大概在讲什么，
并收集「发过相关内容」的 UP 主作为候选拉黑名单。

> **preview 与 block 两个阶段都已实现。** preview 全程免登录只读、不发送任何凭据；
> block 只在用户确认后执行，且凭据全部走 DSH 凭据服务、不落配置、不出现在输出里。

## ⚠️ 先读这一段：使用顺序与风险

**必须「先预览、后拉黑」。** 正确用法是三步，跳过任何一步都可能出事：

1. **`bili_topic_preview`** —— 免登录只读，只拿候选 UP 主名单，**不发送任何凭据**；
2. **人工确认** —— 在候选里勾选/撤销。候选带 `confidence`，`high` 可优先采用，
   但排序衡量的是**证据量而非语义贴近度**，`medium` / `low` 必须看样例标题再决定；
3. **`bili_topic_block`** —— 只有这一步才读凭据、才发写请求，且**必须显式传 `confirm: true`**。
   不传就只回报告、绝不落笔。

### 风险提示（请务必读完）

- **批量拉黑可能被 B 站判定为恶意行为，存在封号风险。** B 站官方**没有**文档化任何拉黑
  频率阈值，社区工具的做法从「每请求 500ms」到「批间隔 2–4 小时、分多天完成」不等。
  同类项目 `bilibili-blocker` 的作者为规避这个风险，**主动放弃调用官方接口**、只用本地屏蔽。
- **黑名单有上限**（社区说法：普通用户约 500、上限 5000，**未获官方确认**）。
  达到上限接口返回 `22008`，本插件会**立即终止**。
- **「相关内容」会误伤。** 同一话题下正常做科普/测评的创作者，会和搬运号、擦边号、
  引战号被关键词粗筛一并命中。**请务必人工勾选，不要对整份列表无差别执行。**
- **第一次真跑请按这个顺序**：先 `dry_run: true` 看执行计划 → 再用 `max_block: 1`
  拿一个你不在乎的账号试水 → 确认无误再放量。**不要第一次就 50 个。**
- 本插件是**第三方工具，与 B 站官方无关**。请遵守 B 站用户协议与当地法律法规，
  仅用于管理你自己的账号体验。

## 安装

本插件是标准 DSH bundle（`package.json` 声明了 `dsh.bundle.patch`），**零依赖、无需构建**。

安装前请先确认两件事：

| 前提 | 说明 |
|---|---|
| 本机已装 **git** | 安装 `github:` 地址前，DSH 会先跑一次 `git ls-remote` 预检（5 秒超时）。没装 git 会直接失败。 |
| 本机能**直接访问 `github.com`** | GitHub 地址**不走 npm 镜像 / 安装源**，必须本机直连。连不上会报「无法连接 github.com」，此时需配置代理；或改填 npm 包名（若该插件已发布到 npm）。 |

### 方式 A：插件页面（推荐，桌面端与网页端都适用）

1. 打开 DSH → 左侧 **「插件 / Plugins」** 页面；
2. 在安装框里填（该输入框接受「包名、GitHub 仓库地址或本地目录路径」）：

   ```text
   github:44488866/bili-topic-block
   ```

3. 点「安装」，装完按提示**重启 DSH**。

### 方式 B：在对话里让 agent 装（桌面端推荐）

> 帮我装插件 `github:44488866/bili-topic-block`

### 方式 C：命令行（**仅适用于非 `desktop` 的 profile**）

```powershell
# web profile 就写 --profile web
dsh plugin --profile <profile名> add github:44488866/bili-topic-block
```

`dsh plugin ...` 会把参数原样转发给该 profile 目录下的 pnpm，
并自动把 `bili-topic-block` 写进该 profile 的 `dsh.profile.bundles`。

> 若 `dsh` 不在 PATH 上，请用你本机安装方式对应的入口（例如 `npx @deepseek-ai/dsh`）执行同样的命令。

### ⚠️ 桌面端（Electron 客户端）不能用命令行

官方桌面端读的是 **`desktop` profile**，而 `dsh plugin` 命令行**按设计拒绝**操作它：

```text
error: profile "desktop" is managed exclusively by the Electron application
```

桌面端的插件只能由客户端自己装——用**方式 A 的插件页面**或**方式 B 的会话内 agent**。
也**不要**改用 `--profile web`：包装上了，但桌面窗口读的不是那个 profile，
表现为"什么都没发生、也不报错"。

### 方式 D：本地开发 / 从本地克隆安装

```powershell
dsh plugin --profile <profile名> add link:D:\你的路径\bili-topic-block
```

`link:` 是软链安装，改源码立即生效；但安装后**不能移动该目录**，移动后须重新 add。
桌面端同样不能用命令行，需在会话内让 agent 以**绝对路径**调用 `plugin_manager` 的 `install_bundle`。

### 生效方式

- 新装一个 bundle 通常**热生效**（安装结果里 `application: "applied"`）；
- **替换已安装包的代码需要重启**才能加载新的 JS 模块；
- 判定是否真的生效，请读安装结果里的 `application` 与 `warnings`，不要靠看进程列表或服务端日志。

## 快速上手

装好并**重启**之后：

```text
1) 让它分析一个视频：
   「用 bili_topic_preview 看一下 https://www.bilibili.com/video/BVxxxxxxxxxx」

2) 看返回的候选（每个带 confidence 与样例标题），挑出你确实要处理的
   —— high 可优先采用，medium/low 必须看标题。

3) 要真的拉黑时（需先配好凭据，见下文「凭据配置」）：
   「用 bili_topic_block 拉黑 mid=xxx，先 dry_run」
   预演通过后去掉 dry_run、带 confirm 真正执行。

4) 手滑了就用 bili_topic_unblock 撤销。
```

> preview **全程免登录、不发送任何凭据**；只有 block 才读凭据，且必须显式传 `confirm`。
> 数量受 `maxBlock` 硬上限约束，达到即停。

## 设计：预览 → 确认 → 执行

| 阶段 | 是否需要登录 | 行为 | 状态 |
|---|---|---|---|
| preview | 否（匿名只读） | 取视频元数据/标签/相关推荐/关键词搜索，聚合出候选 UP 主 | **已实现** |
| 确认 | — | 用户在候选列表里勾选/撤销，避免「相关内容」误伤 | 由对话完成（工具要求显式 `confirm`） |
| block | 是（SESSDATA + bili_jct） | 分批调用 `x/relation/batch/modify`，受数量上限与限流约束 | **已实现**（含撤销 `act=6`） |

## 工具

### `bili_topic_preview`

| 参数 | 必填 | 说明 |
|---|---|---|
| `url` | 是 | 视频链接、`BV...`、`av...` 或纯数字 |
| `max_candidates` | 否 | 本次最多返回多少个候选（1–500，默认取配置 `maxCandidates`） |
| `keywords` | 否 | 额外搜索关键词（最多 10 个），与视频标签一起用于扩候选 |
| `include_source_uploader` | 否 | 是否把源视频自己的 UP 主也算进候选（默认否） |

返回：源视频元数据（标题/分区/时长/标签/简介摘要）、话题关键词、候选列表
（`mid` / 昵称 / 命中条数 / 来源 / 命中词 / 样例标题 / 空间链接）、统计与警告。

候选**默认排除源视频自己的 UP 主**（你给的那条视频的作者），只找「其他人」；
需要一并处理就传 `include_source_uploader: true`。

### `bili_topic_block` / `bili_topic_unblock`

| 参数 | 必填 | 说明 |
|---|---|---|
| `mids` | 是 | 要处理的 UP 主 mid 数组，按重要程度排序；只应来自 preview 返回的候选 |
| `confirm` | 是 | **必须显式传 `true`**；缺省或 `false` 时只回报告、绝不执行写操作 |
| `dry_run` | 否 | `true` 时只校验凭据与登录态、给出执行计划，不调用任何写接口 |
| `max_block` | 否 | 本次上限，**只能调低**；实际上限 = `min(配置 maxBlock, 本参数)` |

`bili_topic_unblock` 复用同一套执行器，只是 `act=6`，用于纠正误拉黑
（注意：它会移除这些用户的黑名单记录，无论当初是谁拉黑的）。

### 凭据配置（执行 block 前必须做）

拉黑是**写操作**，需要两个凭据。插件**只从 DSH 凭据服务读取**，不写死、不落盘、
不写进配置文件，也不会出现在日志或工具输出里：

| 默认名 | 取值来源 | 作用 |
|---|---|---|
| `BILIBILI_SESSDATA` | 浏览器 Cookie 里 `SESSDATA` 的**裸 token** | 身份凭证（所有接口） |
| `BILI_JCT` | 浏览器 Cookie 里 `bili_jct` 的值 | 写操作的 `csrf` 参数，**缺它必定 `-111`** |

名字可用配置 `sessdataRef` / `csrfRef` 改名（名字必须与凭据服务里登记的完全一致）。

#### 第一步：从浏览器取到这两个值

1. 在浏览器登录 `bilibili.com`；
2. 按 `F12` 打开 DevTools → **Application / 应用** → 左侧 **Cookies** → 点开 `https://www.bilibili.com`；
3. 找到 `SESSDATA` 这一行，**只复制它的值**（一串裸 token，**不是**整条 Cookie 头）；
4. 同样复制 `bili_jct` 的值。

#### 第二步：填进 DSH

| 方式 | 做法 | 备注 |
|---|---|---|
| **`.env` 文件**（推荐，已实测） | 在 `$DSH_HOME/.env` 写两行：`BILIBILI_SESSDATA=<值>` 和 `BILI_JCT=<值>`（Windows 默认路径 `C:\Users\<你>\.dsh\.env`） | 文件不存在就新建；**等号两边不要空格、值不要引号**；用**无 BOM** 的 UTF-8 保存 |
| **环境变量** | 在启动 DSH 的环境里设置同名变量 | 优先级**高于** `.env` |

> **关于「凭据管理界面」**：DSH 的设置页目前只有账号 / 模型 / 联网搜索等**特定用途**的密钥入口，
> 并没有给任意凭据名用的通用新增页。所以对 `BILIBILI_SESSDATA` / `BILI_JCT` 这类自定义名字，
> **`.env` 是实际可行的做法。**

> ⚠️ **不要把凭据写进 `cordis.patch.yml`。** 插件不从配置读密钥；
> 配置文件会被提交、会进版本库，而凭据不该。

#### ⚠️ 两个「改了却不生效」的坑

凭据解析顺序是：**启动环境变量 → `.credentials.yaml` 存储 → `.env`**。因此：

1. 如果你以前设过**同名的环境变量**，它会一直压过 `.env`，此时改文件毫无效果；
2. `.env` 是在**启动时**被读取并灌进进程环境的，**改完必须重启 DSH**。

#### 第三步：重启 DSH

判断凭据到底有没有被读到，看报错就能区分：

| 报错 | 含义 |
|---|---|
| `BILI_CREDENTIALS_MISSING` | 文件**没被读到** —— 多半是没重启 |
| `BILI_LOGIN_REQUIRED` | 读到了，但 SESSDATA 无效或已过期 |

#### 第四步：先预演，确认凭据真的可用

```text
bili_topic_block(mids=<随便一个 mid>, confirm=true, dry_run=true)
```

`dry_run` 会真实调用只读的 `nav` 校验登录态，**但不会发出任何写请求**：

- 凭据没配 → 立刻报 `BILI_CREDENTIALS_MISSING`（并指明缺哪一个）；
- 凭据配错或过期 → 报 `BILI_LOGIN_REQUIRED`；
- 一切正常 → 返回执行计划，此时再拿掉 `dry_run` 真正执行。

#### 插件如何处理你的凭据

- 只在 `bili_topic_block` / `bili_topic_unblock` 里读取，**preview 全程不读**；
- Cookie 只发送给 `api.bilibili.com`；
- 任何携带 Cookie 的请求都强制 `redirect: 'error'`，**凭据不可能被重定向带到其他源**；
- 不落盘、不进日志、不进工具输出，进程内存里用完即弃。

## 配置（`cordis.patch.yml` 的 `config`）

按 id 覆盖时 config 是**整体替换、不深合并**，要写全所有想改的字段。

| 键 | 默认 | 含义 |
|---|---|---|
| `requestTimeoutMs` | 20000 | 单请求超时（毫秒） |
| `requestMinDelayMs` | 1200 | 请求间随机抖动下限 |
| `requestMaxDelayMs` | 3500 | 请求间随机抖动上限 |
| `enableKeywordSearch` | true | 是否用关键词搜索扩候选（需 WBI + buvid，免登录） |
| `searchPages` | 1 | 每个关键词搜索页数（0–2） |
| `maxKeywords` | 6 | 最多用几个关键词搜索 |
| `ignoreKeywords` | 见下 | 关键词黑名单（精确匹配）。设为 `[]` 即不过滤 |
| `useTitleAsKeywordFallback` | false | 标签全被忽略时，是否退回用标题当关键词 |
| `includeSourceUploader` | false | 是否把源视频 UP 主计入候选 |
| `candidateMinHits` | 1 | 候选至少要命中几条视频 |
| `maxCandidates` | 60 | 预览最多返回多少候选 |
| `maxBlock` | 50 | block 的数量**硬上限**（1–500），达到即停 |
| `sessdataRef` | BILIBILI_SESSDATA | SESSDATA 的凭据名（只允许字母/数字/下划线） |
| `csrfRef` | BILI_JCT | bili_jct 的凭据名 |
| `batchSize` | 50 | 每个批量请求放几个 mid（1–50，文档上限 50） |
| `batchRestMs` | 60000 | 批次之间的休息毫秒数（只有一个批次时不会触发） |
| `probeFailures` | true | 批量接口未说明原因的失败项，是否单条复探拿精确业务码 |
| `maxProbes` | 10 | 单条复探的次数上限（0 表示不复探） |
| `riskCooldownHintMs` | 600000 | 触发风控时建议的冷却时长，只用于提示 |

`ignoreKeywords` 默认值（**精确匹配**，不区分大小写；只影响关键词搜索，不影响相关推荐与标签展示）：

```text
# 宽泛分类词
解说 / 电影解说 / 影视解说 / 影评杂谈 / 经典 / MV / LIVE / 现场 /
音乐现场 / 流行音乐 / 欧美音乐 / 欧美MV / 教程 / 入门教程
# 抽象类目词
社会 / 人文 / 思维 / 认知
# 标记 / 技法类词
原创 / 生活 / 情感 / 女神 / 剪辑 / 影视剪辑 / 必剪创作
```

这三类词都是实测出来的噪声源：

- **宽泛分类词**把 LOL 教学、经典港片、儿歌、电音节带进候选；
- **抽象类目词**更隐蔽——一条标签为「社会/人文/思维/认知/年轻人/后代」的选题视频，
  靠「人文」把街拍系列刷出 **15 条命中**、靠「认知」拉进认知玄学号、靠「社会」拉进时政新闻号。
  剔除这 4 个词后，聚合数从 133 降到 74，街拍/哲学课/玄学号**全部消失**，
  而「双输好过单赢」「国家对生育的态度」「躺平党四大派系」这类真·同题材内容升到前排。
- **标记 / 技法类词**只说"怎么做的"或"平台标记"，没有内容指向。一条标签为
  「原创/生活/女神/剪辑/影视剪辑/情感」的视频，靠「剪辑」把**知名影视制作教学号**拉了进来、
  靠「女神」「生活」拉进大量擦边号——**15 个候选里只有 2 个真正同题材**。

想完全不过滤就设 `ignoreKeywords: []`；想补充自己的黑名单就往数组里加词。

**关于 `useTitleAsKeywordFallback`（默认 false）**：当所有标签都被忽略时，退回用**标题**去搜
看似能保底，但实测更差——长标题里常夹着口语化、有歧义的短语，拿去当搜索词会字面命中
完全无关的视频（实测：用一条社会议题视频的标题去搜，搜出来的是某格斗游戏招式视频）。
因此默认只靠「相关推荐」并明确告警，需要时再把该开关打开。

未知配置项、越界值、类型错误都会在激活时报错（防止 `maxblock` 之类拼写错误被静默忽略）。

## 实现要点与取舍

- **零依赖**：只用 Node 内建（`node:crypto` 做 MD5）与全局 `fetch`。
  因此没有引入 `defineTool`/`schemastery`，`parameters` 与 `output.schema`
  直接按 registry 的契约写成**标准 JSON Schema**，并自行校验入参。
- **搜索必须双条件**：`x/web-interface/search/type` 需要 **WBI 签名 + buvid Cookie**，
  缺任一项会直接 HTTP 412（实测）。buvid 通过 `x/frontend/finger/spi` 匿名申请，不落盘。
- **只读优先**：相关推荐 `x/web-interface/archive/related` 免登录、免签名，
  一次约 40 条且带 `owner.mid`，是候选主力来源；关键词搜索只作扩量。
- **串行不并发**：所有请求经 `Pacer` 排队，之间插入随机抖动；
  预览阶段遇风控只降级告警并停止继续检索，不影响已拿到的结果。
- **全内存**：无任何落盘；WBI 口令与 buvid 都只存在于进程内存。
- **凭据安全前置**：`apiGet` 一旦携带 Cookie 就强制 `redirect: 'error'`，
  避免凭据被重定向带到其他源（block 阶段直接复用这条约束）。
- **核心与 DSH 解耦**：`lib/` 下**没有任何文件 import DSH 的东西** —— WBI 签名、
  接口客户端、预览聚合、拉黑执行全部是零依赖的纯 Node ESM。DSH 专属的只有
  `index.js` 的 `apply(ctx, config)` 与 `lib/preview.mjs` / `lib/block.mjs` 里那两段
  `register*` 胶水（合计约 130 行，占全量 4%）。`runPreview()` / `runRelation()` 内部
  一个 `ctx` 都没有，凭据是**依赖注入**进去的（`deps.credentials = { resolve(ref) }`）。
  因此要移植到独立 CLI、MCP server 或别的 agent harness，只需换掉那层胶水，
  核心逻辑一行不用改。

## 候选置信度

每个候选带 `confidence`，并按其排序（同档再按命中数）：

| 档 | 规则 | 含义 |
|---|---|---|
| `high` | **相关推荐 + 搜索都命中**（跨来源互证） | 实测这一档基本同题材，可优先采用 |
| `medium` | 单一来源，但有多重佐证（命中 ≥2 条 或 ≥2 个不同关键词） | 需看样例标题判断 |
| `low` | 单一来源 + 单条 + 单关键词 | **混合档**：既有噪声，也含「只发过一条同题材视频」的小 UP 主，**必须看标题** |

> ⚠️ **排序衡量的是「证据量」，不是「语义贴近度」。** 因此它系统性偏向
> **高产号与时政/新闻号**——这类账号同一话题会发很多条，天然容易跨来源命中；
> 而一个只发过一条同题材视频的小 UP 主，只会落在 `low`。
> 实测例：一条社会议题视频的种子，排在前面的全是同类话题的新闻号，
> 而几个只发过一条、但**明显更贴题**的小 UP 主内容全在 `low`。
> **所以不要只看 `high`：`high` 用来快速下手，`low` 才是真·同题材小号的藏身处。**

> ⚠️ **不要以为「相关推荐」就一定可信。** 早期版本按「相关推荐 = 高可信」排序，
> 被一条 13 秒短视频种子推翻：短视频的相关推荐会落进**泛短视频池**（抽象/鬼畜号），
> 而真正的同题材创作者只出现在搜索结果里。因此现在只有**跨来源互证**才算 `high`。

### 弱信号种子告警

当满足以下 ≥2 条时，输出会带一条 `⚠` 开头的告警，提示候选可靠性显著下降：

- 时长 < 60 秒
- 可用标签 ≤ 2 个
- 简介为空（或为 `-`）

这类视频本身几乎没有可识别的内容信号，任何"相关"推断都不可靠。
**遇到告警时请只考虑 `high` 档，或换一个内容更实的视频作种子。**

## 已知限制（含实测数据）

**噪声是真实存在的，本插件只能压低、不能消灭。** 对 5 个视频的实测：

| 种子 | 过滤宽泛词前 | 过滤后 |
|---|---|---|
| 电影解说（潜伏6） | 前 12 里混入 `LOL王者教学`（命中"解说"）、`水下洞穴救援`（命中"潜伏"）、`舌尖上的猫和老鼠` | LOL 教学、猫和老鼠**消失**；温子仁/潜伏6 系占据前列且全部 `high` |
| 演唱会现场 | 混入 `EDC电音节`（命中"LIVE"，5 条命中）、`200首经典儿歌`、`经典港片` | 电音节、儿歌、港片**消失**；前列变为《加州旅馆》神级现场、刘欢演唱会等同题材 |
| AI教程（AI漫剧） | 本就很干净 | 基本不变（只跳过 `入门教程`） |
| 社会议题选题视频（96 秒） | 混入街拍系列（"人文"刷出 15 条命中）、认知玄学号、时政新闻号；聚合 133 | 街拍/哲学课/玄学号**全部消失**；聚合 74，升上来的是同题材的讨论类视频 |
| **情感/剪辑类选题视频**（264 秒） | 标签为 `原创/生活/女神/剪辑/影视剪辑/情感`，15 个候选里只有 **2 个**同题材，其余是影视制作教学号与擦边号 | 已把这 5 类标记词加入默认黑名单（见上）；**这类种子本质上是"标签无内容指向"，插件只能压低噪声，仍需人工勾选** |
| **13 秒 AMV/MAD 短视频** | — | **反例**：`high` 从 4 个降到 0 个，抽象鬼畜号从 `high` 降为 `medium`，并触发弱信号告警（详见上节） |

**剩余的噪声来源（本插件无法解决）：**

1. **关键词歧义**：搜「潜伏」会返回《广西百色水下洞穴救援事件》——词同义不同，任何过滤器都救不了，只能靠人工看标题。
2. **种子自身的垃圾标签**：例如「一口气看」「AI剧情大片」「红果短剧」这类标签本身就是营销词，
   它们不在默认黑名单里（因为对别的视频可能有用），但会把凉菜/擦边短剧带进来。
   遇到这种情况，请在配置里把它们加进 `ignoreKeywords`。
3. **种子本身是合集/搬运视频时**，它的「相关推荐」邻居天然也是同类合集——
   这时候选"噪声"其实可能正是你想处理的对象。

**因此：`high` 档可以直接采用，`medium`/`low` 必须看样例标题再决定。**
不要对整份列表无差别执行拉黑。

**其他：**

- 候选里可能出现**已注销账号**（拉黑会返回 `22013`/`40061`）或**此前已拉黑**的账号（`22120`）。
- 预览本身**不含任何拉黑动作**；是否执行由 `bili_topic_block` 的显式 `confirm` 决定。
- 实测 3 个种子各扫 40 条相关推荐 + 120 条搜索、耗时 23–32 秒、**风控命中 0 次**。

## block 阶段：安全闸门与限流

### 五道闸门（全部有实测）

按代码顺序，任何一道不通过都不会发出写请求：

| # | 闸门 | 行为 | 实测 |
|---|---|---|---|
| 1 | 显式 `confirm: true` | 否则只回报告、绝不落笔 | 0ms 返回，**不触网** |
| 2 | 宿主凭据服务存在 | 缺失即报 `BILI_CREDENTIALS_UNAVAILABLE` | 0ms |
| 3 | `SESSDATA` 与 `bili_jct` 都已配置 | 缺哪个报哪个，不静默失败 | 1ms，消息里指明凭据名 |
| 4 | `nav` 校验登录态 | 未登录报 `BILI_LOGIN_REQUIRED` | 219ms，只发了只读 `nav` |
| 5 | 计划阶段去重/剔除自己/受上限约束 | 不能把自己拉黑、不重复、不超量 | 见离线断言 |

### 数量上限：达到即停、绝不超量

`cap = min(配置 maxBlock, 入参 max_block)`。处理满 `cap` 个后**立即停止**，
剩余标记为 `not_attempted`，`abort_reason` 记为 `cap_reached`，并在告警里写明
「只处理了前 N 个，其余未处理」。**不会**偷偷截断后假装成功。

### 中止条件

| `abort_reason` | 触发 | 后续 |
|---|---|---|
| `risk_control` | `-352` / `-412` / `-799` / `-509` | **立即终止**，给出冷却建议（默认 10 分钟） |
| `blacklist_full` | `22008` 黑名单已满 | **立即终止**，提示先清理黑名单 |
| `auth_error` | `-101` / `-102` / `-111` | 立即终止（凭据失效或 csrf 错） |
| `cap_reached` | 处理数达到上限 | 正常停止，剩余未处理 |
| `confirm_required` / `dry_run` | 未确认 / 预演 | 未发起任何写请求 |

> **关于「长停」的实现取舍**：需求原话是遇风控「长停」。本插件实现为
> **立即终止本次运行 + 给出冷却时长提示**，而不是在工具里睡 10 分钟——
> 工具内长睡只会把调用拖到超时、留下状态不明的副作用。冷却这件事交给
> 用户与对话节奏来控制，更安全也更可控。

### 批量接口是主力

依据文档，`x/relation/batch/modify` 一次最多 50 个 mid，且只支持关注(1)与拉黑(5)。
因此默认 `batchSize: 50`：**默认上限 50 个只发 1 个写请求**，把请求数压到最小。
若你更倾向「慢慢来」，可把 `batchSize` 调成 `1` 并放宽抖动区间
（例如 `requestMinDelayMs: 3000` / `requestMaxDelayMs: 8000`），让每个请求之间隔 3–8 秒。

失败项若批量接口没说明原因，会**限量单条复探**（默认最多 10 次）以拿到精确业务码，
从而区分「已拉黑」（`22120`/`22003`，视为良性）、「已注销/不存在」（`22013`/`40061`，跳过）
与真正的失败。

### 防幻觉护栏

`bili_topic_preview` 会把返回过的 mid 登记在**进程内存**里（不落盘）。
`bili_topic_block` 若收到没登记过的 mid，会在 `unverified_mids` 与告警里点名，
提示「请确认它们来自用户勾选，而不是模型臆造」。进程重启后登记表清空，该检查自动跳过。

### 已知风险（未变）

**批量拉黑仍可能被判定为恶意行为。** B站官方**没有**文档化任何拉黑频率阈值，
社区工具的做法从「500ms 间隔」到「批间隔 2–4 小时、分多天完成」不等。
`bilibili-blocker` 的作者甚至主动放弃官方接口、只用本地屏蔽，理由就是封号风险。
**请从小批量开始，并优先使用 `dry_run` 与 `high` 置信度候选。**
